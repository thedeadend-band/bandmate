# Calendar OAuth and editing

## Implemented in Phase 1

The existing Calendar combines read-only ICS, editable local events and cached
Google events. Calendar managers select sources and explicitly enable their write
policy. Only current Calendar editors/managers can create/update/delete events;
Booking can remain OFF. Source filters use distinct ICS/local/Google identifiers.
Local writes are immediate; Google writes show a durable pending/confirmed/failed/
conflict/ambiguous status and are processed by the independent Google timer.

Forms validate IANA timezones, exclusive all-day end dates, positive durations and
DST gaps/folds. Ambiguous local times require choosing an unambiguous time or UTC.
Existing eligible Google events can be edited; recurring events, invitations with
attendees, private and special events remain read-only. All private event details
are masked in BandMate, including for owners, in this conservative initial release.
No invitations are generated by BandMate (`sendUpdates=none`).

## Operator setup

Configure `BANDMATE_SECRET_KEY_FILE`, `GOOGLE_CALENDAR_CLIENT_ID`,
`GOOGLE_CALENDAR_CLIENT_SECRET`, and an exact registered HTTPS
`GOOGLE_CALENDAR_REDIRECT_URI` ending in `/calendar/manage/google/callback/`.
The client secret is application infrastructure; band refresh tokens stay encrypted
in the DB. Never put them in chat, Git or service command lines.
See [vault operations](OPERATIONS.md).

Managers use Calendar → Manage Calendars → Local and Google calendars. Connect an
account read-only first, wait for the Google timer to refresh its CalendarList,
select a calendar and acknowledge shared-calendar effects. To enable writes,
request event-write consent for that account, then enable the selected source;
a queued live ACL check must succeed before it becomes writable. A broadly scoped
token alone never enables any selected calendar.

Initial scopes: `calendar.events.readonly`, `calendar.calendarlist.readonly`, plus
openid/email to verify identity. Explicit elevation adds `calendar.events` only.
No broad Calendar/ACL administration scopes. OAuth uses encrypted PKCE, single-use
state bound to user/session/Group, ten-minute expiry, fresh manager verification
and account generations; reconnect/disconnect cannot be undone by stale consent.
[Google authorization reference](https://developers.google.com/workspace/calendar/api/auth).

## Synchronization and recovery

`sync_google_calendars` performs bounded paginated sync with tombstones and
per-calendar sync tokens. HTTP 410 resets only that source. Pages validate before
cache/cursor commit; partial failures retain the previous cursor. Initial/full
sync covers the preceding 90 and following 540 days, with weekly full refresh.
Recurring instances appear within that window but cannot be edited.

Every remote write rechecks the actor, source policy, live CalendarList ACL and
latest event. ETags/If-Match prevent overwriting changed Google events. The worker
uses deterministic event IDs and private operation markers to recognize prior
success. Unknown patch/delete outcomes require inspection; never retry an
ambiguous write blindly. Provider read failures and 429s have bounded retries.
Calendar access revocation disables writes and hides stale provider data.

Disconnect clears BandMate's token and hides the source. Managers may separately
revoke the application in their Google account. Selected source/event history is
retained for audit and reconciliation. Shared Google calendars reflect edits for
all their Google users; internal band isolation cannot isolate the shared remote
calendar itself.

Provider adapters and recovery paths are covered with mocked responses. Live
OAuth, Google verification, ACL behavior and end-to-end writes remain staging
acceptance gates requiring explicitly supplied test accounts.
